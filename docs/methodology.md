# Methodology: 为什么交叉评审有效

> 本文档是 PolyReview 的设计依据，来自真实使用数据（两个 host、6+ 轮真实评审、
> 40+ 次评审员调用），也是我们与其他 "LLM review" 工具的差异所在。

## 核心主张

1. **单模型自评是循环论证**。同一个模型（甚至同厂商）生成 → 评审，错误模式
   高度相关。交叉验证要求评审团成员来自**不同厂商**（`identity()` 可核实）。
2. **评审要收敛，不要发散**。自由评语会永远有下一条意见。verdict 协议
   （`APPROVE/REVISE` + severity）把"通过"变成可判定事件：
   **只有 blocker/major 阻塞，minor 记录不阻塞**。
3. **主持人裁决制**。评审员只出意见；采纳/反驳由作者（人或 host LLM）逐条
   处置并留档。复核轮只核对"处置是否合理"，不重提已解决意见。
4. **会话续聊是增益，不是依赖**。每轮请求携带全量上下文（可审计、可复现），
   session_id 续聊只提供缓存红利与"评审员记得自己说过什么"。

## 实证数据点（真实会话）

- 设计方案评审 3 轮收敛：REVISE(2+4 条阻塞) → REVISE(1+1) → 全票 APPROVE
- 双评审员在 3 个不同轮次**独立定位同一问题**（文档与实现不符、承诺未落档、
  协议复用失真）——交叉命中显著高于偶然，这是异构评审团的核心价值
- 评审员具备全仓读取能力时，意见普遍带行号级证据（如 `node_common.py:169`）
- 复核轮续聊（同一 session）下，评审员能逐字复述自己上轮意见——记忆真实存在

## verdict 协议

```json
{"verdict": "APPROVE | REVISE",
 "issues": [{"id": 1, "severity": "blocker|major|minor",
             "point": "问题描述（方案位置或 文件:行号）", "suggestion": "可执行建议"}],
 "summary": "100 字以内总评"}
```

- 解析取回复中**最后一个**合法 json 块（CLI 常先输出思考过程）
- 解析失败按 REVISE 处理，并在下轮 prompt 中强制协议

## 循环（2-4 轮典型收敛）

```
送审（并行、每评审员独立会话）
  → verdict 解析 + session_id 落盘
  → 全票 APPROVE？是：FINAL_REPORT
  → 否：作者逐条处置（采纳=改工件 / 反驳=写理由），写 host_disposition.md
  → 复核轮（续聊 + 全量上下文双保险）→ 回到解析
  → 超过 max_rounds（默认 20）：输出分歧报告，人工裁决
```

## 与 A2A 的关系

同一方法论有两种实现：MCP 路径（本仓库，评审员挂进 host 会话，人机协同仲裁）
与 A2A 路径（评审员作为独立服务节点，任意客户端编排）。两者共享 verdict 协议。
